这个博客是怎么开发的：阅读体验、质量门禁与自动发布

发布于2026-11-21
作者Lvxi
耗时16分钟
约3131字
分类前端
标签Nuxt性能博客

迁移记录写到（六）之后，这个博客安静了一阵。安静不代表停工——这轮集中补了三块东西：把「读」这件事的细节补齐、把内容质量交给构建门禁、把发布流程压缩成一条命令。这篇把整个开发过程摊开讲，包括三个只有线上环境才肯暴露的调试故事。

这轮做了什么

先列清单，后面逐块展开：

  • 阅读体验：排版面板、本地全文搜索兜底、脚注悬浮预览、键盘导航、公式复制、免手自动滚动、404 智能推荐、划词引用分享
  • 性能：先实测再优化，把每页 ~122KB 的内联样式拆出去，HTML 总量从 109MB 降到 57MB
  • 内容质量：健康巡检扩展进 CI，封面引用、日期倒挂、单篇系列都有人管
  • 发布自动化：源码私仓 + 产物公开仓分立，deploy key 跨仓库推送，线上验收探针，Algolia 索引跟随文章变更自动同步

阅读体验：围绕「读」补齐细节

博客的核心动作是读，但读完一轮盘点才发现，「读」周围的细节欠账比想象多。

最大的一个是排版面板：字号、行距、字距、行宽、字体（含一个「书卷模式」）都能调。实现上有个容易踩的坑——阅读设置如果等到 Vue 挂载才生效，刷新瞬间会闪一下默认样式。所以设置存在单个 localStorage key 里，由一段内联的首帧脚本在 <head> 里直接应用，等应用挂载了再接管。这个取舍写进了 ADR（docs/adr/0001）：为什么不用 Pinia、为什么单 key 不拆分、为什么首帧脚本必须内联。

第二个是本地全文搜索兜底。Algolia 不可用（断网、密钥失效）时搜索页不该白屏。实现分两层：摘要级结果（标题 / 摘要 / 分类 / 标签）立即返回，public/search-index/ 的正文分片按需并行拉取，就绪后自动升级成全文结果（命中词周边片段加高亮）。判定语义是词 A 在标题、词 B 只在正文时，两词同篇命中才算 AND；零结果再放宽成 OR 兜底。Service Worker 对 search-index 走 NetworkFirst，拉取过的分片二次离线仍可用；navigator.onLine === false 时直接本地，不再空耗一次远程超时。

剩下的是一组小件，每个都不大但都要处理边界情况：

  • 公式复制：KaTeX 渲染出来的公式复制到手全是 HTML 转义，真正的 LaTeX 源码藏在 annotation[encoding="application/x-tex"] 里，从那里取
  • 免手自动滚动：rAF 按时间差推进（后台标签页卡顿回来不会瞬移），滚轮、触摸、任意按键都能打断，prefers-reduced-motion 用户直接禁用
  • 404 智能推荐：错误页没有默认布局可依赖，单独生成一份轻量 posts-lite.json（500+ 篇标题摘要，约 58KB），按 slug 关键词打分推荐五篇，外加一个直达搜索框
  • 划词引用分享：选中正文浮出「复制引用」，生成 > "文本" — [标题](url#:~:text=…) 格式，链接用 Text Fragment，别人打开自动高亮定位；超过 200 字符切成首尾 30 字的区间语法
  • 外链标识：正文里站外链接统一加箭头图标和新窗口打开提示，读者能预判「这一下会离开本站」

这里有一条这轮反复验证的经验：动手之前先盘点，好几个想法查完发现已经有了。giscus 的 reactions 本来就开着、代码块工具栏早就齐全（复制/折叠/行号/换行/强制深色）、图片灯箱的无障碍也是完整的——如果按计划动手，这些都是重写一遍已有功能。还有个候选是「站内链接悬浮预览卡」，盘点后发现全站正文里内链为零，做出来没有受众，直接砍掉。

性能：先实测，再动手

性能优化的诱惑是直接动手改，这轮逼自己先做了测量：写了个标准库脚本，用 zlib 做 deflate 代理、遍历全部产物统计 HTML 体积、对首屏引用的 JS/CSS/字体去重求和。量出来的结果吓一跳——每页 HTML 里内联着约 122KB 的 <style> 块，全站 592 个页面加起来约 72MB，而且每次导航都重新传输。

修复只要一行配置：

ts
12
// nuxt.config.ts
features: { inlineStyles: false }

组件样式不再逐页内联，改走带缓存的 CSS chunk。实测对比：

指标前后
HTML 体积中位数197KB100KB
HTML 总量109MB57.2MB
dist 总量151.6MB99.6MB
首屏传输（deflate 后）—约 394KB

量完还剩一小块内联：Nuxt UI 的图标 mask CSS 和 @layer 主题变量，每页 13-31KB。这是 Nuxt UI 内部机制，判断不值得追——残余不追和优化要追是同一个决定，都需要数字支撑。顺带发现 KaTeX 产物里 woff/ttf 两种格式只占 dist 不占传输（浏览器只拉 woff2），也就不折腾了。

这轮的教训一句话：不测量就优化，优化的是感觉。感觉通常会选中体感最强、收益最小的那个。

内容质量门禁：把「忘了」变成「构建失败」

文章一多，靠自觉维护质量必败。这轮给健康巡检（check-posts-health）补了几条规则，并接进 CI：

  • 封面引用存在性 = 错误级。封面写了个不存在的路径，列表、详情头图、OG 分享图会一起 404，这个和正文坏图同口径，该拦
  • updatedAt 早于 createdAt = 告警。日期倒挂多半是手滑
  • 系列只有一篇 = 告警，挂在那篇上。多半是 series 字段拼写笔误——想给「Redis 系列」第二篇归队时打错了字，结果成了孤儿
  • 未知 topics = 错误级。主题树之外的 topic 会让主题页聚合出鬼

顺带定了 author 字段的空值语义：缺省回退站点默认作者，空字符串表示明确不署名——版权声明省略署名短语。|| 改 ?? 的一行事，语义却是产品设计。

存量 500+ 篇跑了一遍巡检：0 错误 0 告警过门。这个结果本身就是门禁的价值证明——规则上线的时刻，存量是干净的，之后只有增量需要操心。

发布自动化：从手动搬运到一条命令

这是这轮最有故事的部分。起点很原始：源码只在 Gitee，构建产物手动推到 GitHub Pages。

第一个约束是免费账号的 Pages 只能来自公开仓库，而源码不适合公开。解法是分仓：源码进私仓，产物推公开仓。GitHub 用户站点的规则是仓库名必须等于 用户名.github.io，于是架构变成：

123456789
本地 push（一条命令，双推）
  ├─ Gitee        ← 源码托管（origin 主源）
  └─ GitHub 私仓  ← 触发 CI
       └─ 构建：typecheck → 880+ 测试 → check:health
            → 写出 .env.production（来自 Secret）→ generate:prod
            → check:static 产物校验
       └─ deploy job：deploy key 跨仓库推送 .output/public
            → Pages 公开仓 gh-pages 分支（分支根即站点根）
                 └─ GitHub Pages 自动重新部署

几个关键决策：

  • deploy key 而不是 token：私钥只存在源码仓的 Secret 里，公钥挂在 Pages 仓库的 Deploy keys（勾选写权限），权限面只有这一个仓库
  • 产物走专用 gh-pages 分支：发布 action 是整分支推送，Pages 仓库原来的 master 分支根下挂着 docs/ 结构，会被清掉——专用分支根即站点根，旧 master 原样保留当存档
  • 生产配置走 Secret：整份 .env.production 文本存 ENV_PRODUCTION，构建前写出，不入库；未配置时走 config.ts 兜底值，产物与本地等价
  • 上线验收自动化：probe:site 对线上逐项探测——首页 / 归档 / 关于 / 404 机制 / sitemap / RSS / 抽样文章，抽样的文章从 sitemap 里随机取，防止固定样本变成「永远检查那几篇」

三个只有线上才肯暴露的故事

一、本地全绿，CI 红

发布流水线第一次跑，测试步挂了：一串 unhandled rejection，报错指向竞态测试文件，但本地同一份代码 881 个测试全绿。Windows 与 Linux、4 核与多核——先别猜，先复现。

试了 npx vitest run --maxWorkers=1（单 worker 串行跑全部文件），本地当场复现，失败数字还随文件分组漂移——和 CI 一样。根因：useSearch 里有个模块级的 clientPromise 缓存，vitest 的 vmForks 池在少 worker 时会让多个测试文件共用一个 worker，静态 import 拿到的是上一个文件创建的 client，里面固化着那个文件的远程 mock 和 deferred 实现。于是竞态测试断言错乱、本文件的 deferred 永远没人消费，reject 后变成 unhandled rejection 把整个文件判失败。本地多 worker 时每个搜索文件基本独占 worker，所以一直是绿的。

修复是测试侧统一改成 vi.resetModules() 加动态 import（仓库里唯一从不失败的那个测试文件本来就是这个写法），再给测试用的 deferred 挂一个空 catch 保险。教训：环境差异型问题，第一步是造出本地复现，而不是对着日志猜。

二、中文排序，两台机器两种结果

单 worker 复现后还剩一个测试文件挂：「facet 顺序意外」。那是纯函数测试，没有 mock 没有异步，怎么会跟环境有关？答案是 localeCompare：facet 同数量时按名称决胜，两个中文值「并发」和「前端」，在 Windows 的 zh-CN locale 下按拼音排，并发 在前；CI 的 ubuntu 是 en locale，CJK 按码点排，前（U+524D）在 并（U+5E76）前——顺序直接翻转。

仓库里的构建脚本早就写着注释：「排序用字节序而非 localeCompare，保证任何环境下产物逐字节一致」——前人踩过的坑，注释里都是痕迹，只是轮到自己踩的时候没想起来翻。测试的修复是同数 tie 只断言集合与计数，tie 内排序契约交给 ASCII 用例；生产代码不改（浏览器里跟随用户 locale 排序本来就是对的）。

三、404 页验收 FAIL，但线上其实是对的

probe:site 首次对线上验收，404 相关两项 FAIL，第一反应是发布有问题。抓包看线上响应：/404.html 返回 200、未知路径返回 404、没有跳转——完全正确。问题出在探针自己：判定按「静态 HTML 里必须有 404 标记」的假设写的，而 Nuxt 对 error.vue 的预渲染产物是一个客户端壳——data-ssr="false"、静态 HTML 里没有 title 没有 h1，内容全靠 JS 注水。

这是个从没对过真实产物的检查器：写的时候对着想象中的产物写测试，全绿；上线第一次遇到真实产物就翻车。校准后 404 类的断言改成「状态码正确 + 不跳走 + body 确实是我们的产物」。教训：验证器的假设要拿真实产物校对一遍，尤其是它从来没在真实环境跑过的时候。

Algolia 索引也自动了

搜索索引原来靠手动：Actions 里勾选一个输入框才会推送。现在加了一个变更检测 job，checkout 全历史后 git diff 对比本次推送的 before/after 是否动了 content/posts——动了且构建全绿，索引同步自动执行；只改代码则索引不动。基线不可得（新分支首推、force push）宁可多同步一次，覆盖是幂等的，漏同步才是真问题。

这篇文章就是这条链路的第一个端到端测试：写完 push，流水线里应该能看到 检测文章变更 → posts=true → 同步 Algolia 索引 一路绿到底，然后搜索标题就能命中。

写在最后

这轮的节奏和迁移那次不同：先盘约束和方案再动手，每个功能带着回归测试落地，门禁全绿才进主干。盘点下来几十个提交里几乎没有「先写后返工三遍」的——不是一次写对了，是验证跑在提交前面。把约束写清楚，方案的选择题就变成了证明题，这句话在迁移记录里写过，这轮算是又验证了一遍。

写这篇的晚上没下雨，窗外很安静，流水线在对面跑得也很安静。

写完舒坦了，收工。
